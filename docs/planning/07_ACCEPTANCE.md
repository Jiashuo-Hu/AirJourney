# 07 · v0.0 功能验收计划

日期：2026-10-10 · 版本保持 v0.0 · 本轮按负责人最新指示聚焦基本功能与实际体验。

## 1. 当前验收依据

检查项目架构、代码、资源、交付文件、自动测试和实际 App 操作，判断个人飞行记录的基本使用流程是否成立，并发现可复现的功能 bug、逻辑缺陷及体验改进项。

本轮不进行通信权限、网络安全、文件路径安全、攻击测试、地图政治边界审查、审图或资源许可审查。它们不属于通过条件。项目目录和测试输出位置保留作为操作说明；不删除产品已有代码或资源，也不改写过去报告中的历史事实。

此前文档中的 Must 是设计目标，本轮不要求所有高级能力、极端场景、硬件矩阵或理想性能全部达成才通过。以基本功能可用为准：影响主要使用流程或导致正常操作丢数据的问题阻断通过；其余不足真实记录并安排后续迭代。本文优先于旧实施报告、历史验收意见和其他文档中冲突的检查要求。

## 2. 必须实际验证的使用闭环

1. 启动应用，手动新增航班，选择或填写起降地点、航司和时间等信息；修改、保存、重启后内容仍在。
2. 未知时间、目录外资料和缺坐标记录可以保存；补齐坐标后绘制路线，不编造缺失信息。
3. 地球可旋转/缩放，机场和路线可见，列表与地图选择联动，侧栏能隐藏恢复。
4. 机场、航司、联盟、机型的基础编辑和已有 SVG 的展示/导入可用；基本主题和路线样式设置能保存。
5. 搜索筛选、删除恢复、时间/距离基本展示及计算正常；备份导出和恢复保留记录与个人资料。
6. 当前设备上的可运行程序/安装包正常使用，界面默认英语，主要按钮可达；本地资源可用且不要求在线航班查询。

标签、个人字段、完整联盟 Logo 集合、全部主题组合、极端日期/数量、所有 DPI/显卡/干净 VM 和精细性能属于进一步核验与改进范围。仍可测试并报告，单项不足不自动阻断整体基本功能验收。若某问题影响上述基本闭环，则按实际影响提升严重度。

## 3. 独立检查方法

先读当前规划与 docs/implementation，再查实际源码、package.json、测试、资源和 release 产物。实际栈为 Electron、React/TypeScript、CesiumJS 和 SQLite WASM；不用原计划 Tauri/Rust 作为否决条件，检查当前职责划分、状态流转、存储/绘图逻辑和可维护性。

记录所测 App、安装包和源码版本/标识，核对交付清单；运行现有构建/测试并补充有价值的独立功能用例。至少实际打开 App 完成新增→保存→地图→编辑→重启→备份恢复流程，不仅阅读代码或复用已有报告。使用独立测试数据，避免改动用户真实记录。

已有自测与 docs/acceptance 中的内容只作参考；新一轮结果写入新的验收子目录，不覆盖原证据。不能执行的检查标 NOT RUN 或 BLOCKED，说明限制；不得因旧报告写过通过便直接继承。

## 5. 缺陷分级与通过规则

- P0：正常操作丢失/破坏记录，或程序反复崩溃、核心流程整体不能使用。阻断通过。
- P1：新增保存、主要地图呈现、基础编辑、持久化或正常备份恢复等基本能力明显错误/不可用。阻断完整通过。
- P2：局部功能、复杂输入、次要定制或特定显示场景存在问题，基本流程可用。列修复建议，通常不阻断。
- P3：视觉、文案、交互细节、维护性或性能提升。列后续改进建议。

PASS：基本闭环已实测可用，无开放 P0/P1；允许存在已公开的 P2/P3和补充项未测。FAIL：已复现基本功能阻断。BLOCKED：关键使用测试无法完成、无法形成结论。CONDITIONAL：仅明确限定场景可用，需说明条件及影响；不能用它掩盖已复现阻断。

已撤出的审查项不记为产品 FAIL，不沿用过去地图边界缺项的阻断结论。缺少某个 Logo、某个高级入口或某种测试设备不自动判整体失败；如实报告现状，按实际功能影响分类。

## 6. 报告与下一版本建议

本轮写 docs/acceptance 下新的子目录，至少包含 report.md、acceptance_results.csv、issues.md 和 screenshots/logs 等证据。汇报所测版本/环境、基本功能结论、逐项覆盖、已复现问题、未测项以及改进优先级。

每个缺陷记录 ID、P0–P3、对应功能、复现步骤、预期/实际、截图或日志、影响、修复方向和复测条件。将必修 bug、非阻断不足、后续功能增强分开，不把设计偏好说成确定 bug；建议版本由负责人决定，本轮不升级 v0.0。

验收 Agent 不直接修改产品代码或替用户解决实现任务。保留真实记录和已有报告，新增独立证据，最终用简洁中文向负责人汇报。
